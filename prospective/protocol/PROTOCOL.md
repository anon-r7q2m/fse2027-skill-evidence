# Prospective decision-boundary study v1

Selection fixed: 2026-09-29, before target implementation inspection or execution.
Status: methods reviewed; public version pins and diagnostic packets pending.

## Authorization and objective

The user authorized the proposed bounded prospective validation on September29
and removed the deadline-based time pressure. The objective is to test concrete
predictions outside the paper's development cases, not to obtain a target review
score. This is a new study. All previous benchmark and diagnostic versions remain
closed. No new paid provider call, benchmark grading, Docker use, or credential
access is part of this study. In-product diagnostic agents and trusted local
commands inside owned temporary workspaces are permitted by the research task.

## G0: targets and independent obligations

The two fixed families are Hugging Face `smolagents` (CodeAgent final-answer
checking/acceptance) and Microsoft `autogen` (local code execution through a
CodeExecutorAgent and team termination). Selection is purposive for public
Python source, local execution, and an actual receiving decision. It is not
based on a known bug, observed score, or issue report. Public repository landing
pages were read; implementation, issue discussions and runtime results were not.
Pin each repository's public default-branch HEAD at acquisition. Do not replace
a target after seeing results. A missing/non-runnable specified interface is
reported as not evaluated, not followed by a favorable substitute.

A bounded filename-only exposure search found no `smolagents`,
`microsoft/autogen` or `autogen.agentchat` match in project paper/extraction/core
notes and design/protocol entries. This is not proof of no historical/model
training exposure. Diagnostic participants disclose familiarity; only current
session runtime-result non-exposure is controlled.

An error requires an obligation from the pinned public API/configuration or an
independent execution fact. A model giving a wrong answer, or a nonzero exit
followed by termination, is not automatically a framework defect. The diagnostic
participant must identify the exact promise and consumer; unclear promises are
INCONCLUSIVE. Distinguish interface violation, application configuration hazard,
legitimate behavior, and unsupported allegation.

## G1: diagnostic inputs and allocation

Use four fresh in-product contexts, one per family/arm. Family-specific opaque
slots are assigned to baseline or principle guidance by a recorded random seed
before source reading. All inherit the same default model and common tools;
the exact server model/version and model training exposure are not independently
attested. Each session has at most90 minutes of static diagnosis from dispatch.
Record actual elapsed time and accessible tool-use counts; do not invent token
or human-effort estimates. A participant may finish early or ABSTAIN.

Both arms receive identical pinned source, public docs/tests, interface scope,
output schema, and execution limits. The baseline may trace calls, inspect
contracts, test syntax/status/caller-input conditions, and design strong direct
checks. The principle arm's sole additional material is the frozen three-step
object/property/consumer analysis. Neither receives the paper, historical case
results, other-arm outputs, issue discussions, or a requested positive finding.
No target execution/import, replay, test run or behavioral probing is allowed
during diagnosis; static source/docs/tests may be read. Repository procedural
test instructions do not override this study's explicit no-execution phase.

Each family/arm may freeze at most one primary prediction, two trigger inputs,
two legitimate control inputs, and one local source intervention. Controls must
include ordinary successful acceptance and legitimate handling of execution or
checking failure. More inputs are not more independent discoveries. A valid
abstention can identify no concrete defect or an insufficient public obligation.

## G2: prediction, script and intervention freeze

Each record specifies exact native entry, evidence producer and consumer,
public obligation, expected original decision, expected intervention decision,
input and oracle, source references, and normal behavior to retain. A framework
configuration hazard is not relabeled as an upstream implementation bug.

Use full imports of the pinned implementation, not extracted function slices.
The only substituted external component is a scripted provider/model. Each
finite script and allowed call shape is fixed before any behavior runs, used
unchanged for original and intervention, and cannot branch on arm/variant or
runtime observation. An unexpected call or script exhaustion is INCONCLUSIVE,
not a successful repair. At most8 scripted responses and native max_steps /
team max_turns no greater than8 per input. Capture real local execution facts,
native messages, and actual acceptance/termination events. This measures a
controlled native workflow, not a live model's policy or benchmark utility.

Record diagnostic code, input JSON, patch, obligations, and their digests before
G3. Oracle qualification is a static check after both submissions; it cannot
repair a weak prediction by inventing a new obligation or input. An invalid
oracle/patch remains recorded. No target behavior runs before all four records
are sealed or their allotted opportunities explicitly close.

## G3: common execution and repairs

For each family, run the union of both arms' frozen inputs on original and each
arm's independently patched copy, with the same script and initial state. Never
stack patches. Duplicate inputs may share identical execution, while preserving
their origin. Each run gets an owned directory, clean explicit environment,
120-second process timeout and local command timeout no greater than10 seconds.
Only trusted frozen local Python/print/exit/file operations in that directory
are allowed; no network, external service, personal files, or model API.

Dependency installation and import-only feasibility checks do not count as
behavioral findings. Preserve any failures. At most two fixture-wiring repairs
per family are allowed for demonstrable import/API/harness mistakes; record
original source, failed attempt and the change. They must not change frozen
inputs, promises, predictions or expected decisions. Semantic changes are
exploratory and excluded from confirmation. A non-applicable patch or semantic
repair failure is a result, not an invitation to tune until it passes.

## G4: adjudication and stopping

Primary endpoint per prediction: the independently justified wrong consumer
decision occurs; its predeclared local intervention removes it; all legitimate
controls remain correct. Record these as separate fields, with contradictory,
unknown, not-triggered and not-evaluated outcomes retained. Small patch size
does not establish minimality. Use an adjudicator who did not construct the
prediction, conceal arm labels where possible, and record residual content
unblinding. Unresolved disputes remain INCONCLUSIVE.

The two families close after their fixed opportunities and allowed wiring
repairs. No replacement for negative findings, no result-directed extensions,
and no sample-size/significance claim. One diagnostician per family/arm and two
purposively chosen families cannot establish general method superiority or
human/developer benefit. If the baseline achieves the same boundary/repair,
there is no observed method increment on that case. New native case knowledge
and a negative diagnostic comparison remain legitimate outcomes.

Report all findings, exposure, arm comparisons, limitations and source licenses;
update the manuscript only with actual evidence. Original experiment scores,
private annotations and full historical provider requests remain untouched.
